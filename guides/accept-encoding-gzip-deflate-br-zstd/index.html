Accept-Encoding: gzip, deflate, br, zstd (tested)

Accept-Encoding is the list of compressions the client can unpack; the server answers with one of them in Content-Encoding. We checked what browsers and common clients actually advertise, what breaks, and how much Brotli saves over gzip.

The key result: Chromium only offers br and zstd on secure origins (https and localhost). Testing on http://localhost shows br working, then the same server on a plain-http IP or hostname gets gzip, deflate. Always pick the encoding from the request's Accept-Encoding; never send br because "all browsers support it".

Brotli's advantage comes from high quality: br 11 was 18% smaller than gzip 9 on the script, but about 30 times slower. At fast settings (br 4, zstd 3) the output was about the same size as gzip 6 or slightly larger. So: pre-compress static files with br 11 at build time, and use gzip, a low br quality or zstd for responses compressed on the fly.

4. Serving pre-compressed files (tested Node example)

import http from 'node:http'; import fs from 'node:fs';
http.createServer((req, res) => {
  const file = 'dist/app.js';                // map req.url to a file in real code
  const ae = req.headers['accept-encoding'] || '';
  const headers = { 'Content-Type': 'text/javascript', 'Vary': 'Accept-Encoding' };
  let path = file;
  if (/\bbr\b/.test(ae) && fs.existsSync(file + '.br')) { path += '.br'; headers['Content-Encoding'] = 'br'; }
  else if (/\bgzip\b/.test(ae) && fs.existsSync(file + '.gz')) { path += '.gz'; headers['Content-Encoding'] = 'gzip'; }
  headers['Content-Length'] = fs.statSync(path).size;
  res.writeHead(200, headers); fs.createReadStream(path).pipe(res);
}).listen(8080);

Results with curl: no Accept-Encoding gave 245,232 bytes uncompressed, gzip, deflate gave gzip at 57,868 bytes, and Chrome's gzip, deflate, br, zstd gave br at 47,313 bytes; the --compressed output was byte-identical to the original. Create the files with zlib.brotliCompressSync(buf, {params: {[zlib.constants.BROTLI_PARAM_QUALITY]: 11}}) and zlib.gzipSync(buf, {level: 9}). Vary: Accept-Encoding stops shared caches from serving br to a client that cannot read it. This simple regex ignores q=0; a full parser should honour it.

5. Checking with curl

# ask like Chrome on https, show what came back

# download and decode (curl 8.14.1 built with brotli and zstd: check 'curl --version' Features)

Without --compressed curl sends no Accept-Encoding and, if a server compresses anyway, writes the compressed bytes to your terminal. Frequently asked questions

Why does Chrome send Accept-Encoding: gzip, deflate, br, zstd?

It can decode all four. In our Chromium 153 test it sent that list on https and on http://localhost, but only 'gzip, deflate' on plain http to a non-localhost address.

Is Brotli (br) better than gzip?

At high quality, yes: br 11 made a 245,232-byte script 47,313 bytes vs 57,868 for gzip 9 (18% smaller) but took 466 ms vs 15 ms. At quality 4 it was no smaller than gzip 6. Pre-compress static files with br 11.

What causes ERR_CONTENT_DECODING_FAILED?

The Content-Encoding header does not match the body or the client: a gzip body labelled br, a plain body labelled gzip, or br sent to a Chromium page on plain http that only offered gzip, deflate. All three failed in our test.

Does curl support Brotli?

Yes if built with it: curl 8.14.1 on Debian lists brotli and zstd in Features. With --compressed it sends 'deflate, gzip, br, zstd' and decodes them; without it it sends no Accept-Encoding.

Does Python requests decode br?

Only with the brotli package installed. Without it requests 2.32.3 sent 'gzip, deflate', and a br response came back as raw compressed bytes. Node 24 fetch decoded br and zstd even though it only advertised gzip, deflate.
