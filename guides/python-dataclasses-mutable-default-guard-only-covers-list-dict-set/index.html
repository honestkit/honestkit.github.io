dataclasses: Mutable-Default Guard Only Covers list/dict/set (tested)

One of the selling points of @dataclass over plain classes is that it catches the classic "mutable default argument" trap -- give a field a list default and it refuses to even define the class. We measured whether that protection extends to any mutable default, or only to the specific built-in types it explicitly checks for.

1. list/dict/set defaults are blocked with a clear error

from dataclasses import dataclass

@dataclass
class Foo:
    items: list = []
ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory

Measured: @dataclass raises ValueError at class-definition time for a bare list/dict/set default, pointing you at default_factory instead. This is a real improvement over plain classes, where the equivalent function-default-argument mistake just silently shares one list across every call.

2. A custom mutable class default is not caught at all

from dataclasses import dataclass

class Bucket:
    def __init__(self):
        self.items = []

shared = Bucket()

@dataclass
class Container:
    bucket: Bucket = shared

a = Container()
b = Container()
c = Container()
a.bucket.items.append(1)
b.bucket.items.append(2)
print(a.bucket.items, b.bucket.items, c.bucket.items)
print(a.bucket is b.bucket is c.bucket)
[1, 2] [1, 2] [1, 2]
True

Measured: the class defines itself without any error, and all three Container instances share the exact same Bucket object as their default. Mutating it through one instance (a.bucket.items.append(1)) is visible through every other instance, including ones created before or after. dataclasses's mutable-default check only inspects for the three specific built-in container types -- it has no general notion of "is this default mutable," so any custom class (even one that's obviously mutable, like this one with a growable list inside) sails through untouched.

3. The fix: default_factory for any mutable default, not just the built-in three

from dataclasses import dataclass, field

class Bucket:
    def __init__(self):
        self.items = []

@dataclass
class Container:
    bucket: Bucket = field(default_factory=Bucket)

a = Container()
b = Container()
a.bucket.items.append(1)
print(a.bucket.items, b.bucket.items)
print(a.bucket is b.bucket)
[1] []
False

Measured: using field(default_factory=Bucket) calls Bucket() fresh for every instance, so a and b get independent objects. The rule of thumb @dataclass's own error message suggests for list/dict/set actually applies to any mutable type you use as a default -- the module just doesn't enforce it for anything beyond those three built-ins.

Frequently asked questions

Does @dataclass protect against all mutable default values, or just list/dict/set?

Only list, dict, and set -- we measured a custom mutable class used as a field default passing through with no error at all, and every instance of the dataclass silently sharing that one default object.

Why doesn't Python's dataclass module raise an error for a mutable custom-class default?

Because its mutable-default check specifically tests for the list, dict, and set types rather than checking general mutability -- we confirmed a hand-written class with a mutable list attribute inside it triggers no warning or error as a default value.

How do I avoid the shared-default bug for a custom class field in a dataclass?

Use field(default_factory=YourClass) instead of a bare instance as the default -- we measured this correctly creating a fresh, independent object for every new instance of the dataclass, instead of sharing one object across all of them.

Is a mutable default value in a dataclass the same bug as Python's mutable default argument trap?

Yes -- we measured the exact same symptom: one default object gets created once and shared by every instance, so mutating it through one instance is visible through all the others, identical in shape to the classic 'def f(x=[])' function-default bug.

Does field(default_factory=...) work for custom classes, not just list/dict/set?

Yes -- we confirmed default_factory accepts any zero-argument callable, including a custom class's constructor, and correctly produces a fresh independent instance for each dataclass object created.
