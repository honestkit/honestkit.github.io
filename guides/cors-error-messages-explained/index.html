CORS error messages explained (tested)

Every CORS error in Chrome starts with Access to fetch at '...' from origin '...' has been blocked by CORS policy:. The part after the colon tells you the cause. We broke an Express API in 16 different ways and recorded the exact message Chromium 153 printed for each one.

1. How we tested

One Express 5.2.1 server on port 8986 served a blank page and an API. The page was loaded from http://127.0.0.1:8986 and called the API at http://localhost:8986. Different host means different origin, so every call was cross-origin. Each API route sent a different set of CORS headers. A Playwright script ran fetch() in the page and collected messages with page.on('console').

Every failed case printed two console errors: the CORS message and Failed to load resource: net::ERR_FAILED. In JavaScript, every failed fetch() rejected with the same TypeError: Failed to fetch. The script cannot see which rule failed. Only the console can.

3. The request often reached your server

CORS is enforced by the browser, not the server. Our server log shows that for every simple GET (the first 7 rows), the handler ran and returned 200. The browser received the body and then refused to hand it to the page.

For requests that need a preflight (PUT, DELETE, custom headers, JSON body), only the OPTIONS request arrived when the preflight failed. The real request was never sent.

curl and Node.js never show CORS errors, even with a fake Origin header. Against the route with no CORS headers at all:

So "it works in curl / Postman" proves nothing about CORS. And CORS is not access control: anyone outside a browser can still call your API.

4. A preflight trap in Express

If you set the CORS header only inside app.put(), Express answers OPTIONS on its own. We measured it: status 200, Allow: PUT, body PUT, and no CORS headers. Chromium then reports "Response to preflight request doesn't pass access control check: No 'Access-Control-Allow-Origin' header is present on the requested resource." Put CORS in middleware that runs before the routes.

5. A working Express setup

This middleware passed our hardest test: a PUT with credentials: 'include', Content-Type: application/json and X-Api-Key. Chromium sent one OPTIONS and one PUT, and the fetch returned 200.

const ALLOWED = new Set(['https://app.example.com', 'http://localhost:5173']);

app.use((req, res, next) => {
  const origin = req.headers.origin;
  if (ALLOWED.has(origin)) {
    res.set('Access-Control-Allow-Origin', origin);
    res.set('Access-Control-Allow-Credentials', 'true');
  }
  res.vary('Origin');
  if (req.method === 'OPTIONS') {
    res.set('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
    res.set('Access-Control-Allow-Headers', 'Content-Type, X-Api-Key');
    res.set('Access-Control-Max-Age', '600');
    return res.sendStatus(204);
  }
  next();
});

For the allow-list pattern in more servers, read CORS: allow multiple origins. Why Vary: Origin matters for caches is in Vary: Origin and CORS caching. To cut repeat preflights, see Access-Control-Max-Age.

Header deep dives: Access-Control-Allow-Credentials, Access-Control-Allow-Headers, Access-Control-Allow-Methods, the Origin header.

6. Debug checklist

  • Copy the text after "blocked by CORS policy:" and find it in the table above.
  • If it says "Response to preflight request", look at the OPTIONS request in the Network tab, not the real one.
  • Check the actual headers with curl: curl -i -X OPTIONS -H 'Origin: https://your.site' -H 'Access-Control-Request-Method: PUT' URL.
  • If the message is "No 'Access-Control-Allow-Origin'" on a route that usually works, check for a server error or a proxy that strips headers.
  • Do not "fix" CORS with mode: 'no-cors'. Per the Fetch spec (not measured here), it gives your code an opaque response it cannot read.

Frequently asked questions

Why does my API work in curl or Postman but not in the browser?

CORS is only enforced by browsers. In our test, curl and Node.js fetch got 200 and the full body from a route with no CORS headers at all. Chromium got the same 200 but blocked the page from reading it.

Does a CORS error mean my server never got the request?

Not always. For simple GET requests our server ran the handler and returned 200 every time; the browser hid the response. For PUT, DELETE, JSON bodies or custom headers, a failed preflight means only the OPTIONS request arrived.

Can I see which CORS rule failed from JavaScript?

No. Every failure we tested rejected with the same TypeError: Failed to fetch. The specific reason is only in the browser console.

Why does Content-Type: application/json cause a CORS error?

application/json is not one of the content types allowed without a preflight. Chromium sent an OPTIONS request and reported 'Request header field content-type is not allowed by Access-Control-Allow-Headers in preflight response' until we added Access-Control-Allow-Headers: Content-Type.

Can I use Access-Control-Allow-Origin: * with cookies?

No. With credentials: 'include', Chromium 153 rejected * and also required Access-Control-Allow-Credentials: true in lowercase. Echo the exact allowed origin and add Vary: Origin.
