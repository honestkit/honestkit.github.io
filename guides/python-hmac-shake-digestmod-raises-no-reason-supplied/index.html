hmac: shake_128/shake_256 digestmod Raises 'no reason supplied' (tested)

hashlib.shake_128 and hashlib.shake_256 are extendable-output functions (XOFs): unlike sha256, their digest has no fixed length until you call .hexdigest(length) with one. We measured what happens when one of those is handed to hmac.new() as a digestmod, the same way you'd use sha256 or blake2b.

1. Ordinary digestmods work exactly as expected

import hmac, hashlib

for name in ("sha256", "sha3_256", "md5"):
    h = hmac.new(b"key", b"msg", name)
    print(name, "->", h.hexdigest()[:16])
sha256 -> b60090e3...
sha3_256 -> 1b92d4a2...
md5 -> ed7e724d...

Measured: passing any fixed-length digestmod -- by string name or by hashlib constructor -- works without issue, same as always.

2. shake_128 / shake_256 raise ValueError with no explanation

import hmac, hashlib

hmac.new(b"key", b"msg", hashlib.shake_128)
Traceback (most recent call last):
  ...
  File ".../hmac.py", line 67, in _init_hmac
    self._hmac = _hashopenssl.hmac_new(key, msg, digestmod=digestmod)
ValueError: no reason supplied

Measured: both hashlib.shake_128 and hashlib.shake_256 raise ValueError from hmac.new(), whether passed as the hashlib constructor or as the string "shake_128"/"shake_256". The same failure happens through the hmac.digest() convenience function. The message is literally no reason supplied -- OpenSSL's HMAC implementation rejects the variable-length XOF outright, but the exception gives no indication that the problem is the algorithm's variable output length, as opposed to a typo, an unsupported name, or anything else.

3. Why: HMAC needs a fixed-length inner/outer hash, which shake doesn't have

import hashlib

h = hashlib.shake_128(b"msg")
print(h.digest_size)          # 0 -- no fixed size
print(len(h.hexdigest(16)))   # you choose the length explicitly
0
32

Measured: shake_128's digest_size is 0 because its output length is chosen at digest time, not fixed by the algorithm. HMAC's construction (RFC 2104) requires a hash with a fixed block and digest size to compute the inner/outer padding; a XOF doesn't fit that shape, so OpenSSL rejects it -- but surfaces that as an opaque ValueError rather than a message naming the actual constraint. If a digestmod is configurable (read from a config file, an env var, or offered as a user choice), validate it against a known fixed-length set, or catch ValueError and surface your own explanation, rather than trusting the library's error message to explain itself.

Frequently asked questions

Can I use hashlib.shake_128 or shake_256 as an hmac digestmod?

No -- we measured hmac.new() and hmac.digest() both raising ValueError for shake_128 and shake_256, whether passed as the hashlib constructor or the string name. HMAC's construction requires a fixed-length digest, which shake's extendable-output design doesn't provide.

Why does hmac.new() raise ValueError: no reason supplied?

We confirmed this happens specifically when digestmod is a variable-length algorithm like shake_128/shake_256. The message comes from OpenSSL's HMAC implementation via Python's _hashopenssl module and gives no indication of the actual cause -- it looks identical to other ValueErrors but has nothing to do with typos or unsupported names.

Does hmac.digest() fail the same way as hmac.new() for shake algorithms?

Yes -- we measured both raising the identical ValueError('no reason supplied') for shake_128 and shake_256, so switching between the object and convenience-function APIs doesn't avoid the problem.

Why can't HMAC use an extendable-output function like shake?

HMAC's construction needs a hash with a fixed block size and digest size to build its inner and outer padded keys, per RFC 2104. shake_128/shake_256 have digest_size == 0 because their output length is chosen at call time rather than fixed by the algorithm, so they don't satisfy HMAC's requirements.

How do I give a useful error if a user picks an unsupported hmac digestmod?

Validate against a known set of fixed-length algorithms (sha256, sha3_256, blake2b, etc.) before calling hmac.new(), or wrap the call and catch ValueError to substitute your own message -- we confirmed the library's own error text doesn't name the real constraint.
