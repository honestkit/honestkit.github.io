decimal: quantize() Defaults to Round-Half-to-Even, Not Round-Half-Up (tested)

Most people learn "round half up" in school: 2.5 rounds to 3, 0.5 rounds to 1. We measured what decimal.Decimal.quantize() actually does with exact halfway values under Python's default context, since decimal is often reached for specifically to get predictable, exact rounding for money.

1. The default rounding mode isn't round-half-up

from decimal import Decimal, getcontext

print(getcontext().rounding)

for v in ("0.5", "1.5", "2.5", "3.5"):
    d = Decimal(v)
    print(v, "->", d.quantize(Decimal("1")))
ROUND_HALF_EVEN
0.5 -> 0
1.5 -> 2
2.5 -> 2
3.5 -> 4

Measured: the default context rounding mode is ROUND_HALF_EVEN -- "banker's rounding" -- which rounds an exact halfway value to whichever neighbor is even. 0.5 rounds down to 0, and 2.5 rounds down to 2, not up to 3 as school-taught "round half up" would predict. This is the IEEE 754 / general-decimal-arithmetic standard default, chosen because it doesn't statistically bias repeated roundings upward -- but it's the opposite of what most non-numerics developers assume.

2. ROUND_HALF_UP gives the "normal" behavior, but you have to ask for it

from decimal import Decimal, ROUND_HALF_UP

for v in ("0.5", "1.5", "2.5", "3.5"):
    d = Decimal(v)
    print(v, "->", d.quantize(Decimal("1"), rounding=ROUND_HALF_UP))
0.5 -> 1
1.5 -> 2
2.5 -> 3
3.5 -> 4

Measured: passing rounding=ROUND_HALF_UP explicitly to quantize() gives the conventional result every time a value is exactly halfway -- 0.5 and 2.5 now round up. Code that quantizes without specifying rounding silently inherits ROUND_HALF_EVEN from the default context instead, which only shows a visible difference on exact halfway values -- easy to miss in testing if test cases don't happen to land exactly on x.5.

3. Why it matters: splitting a charge evenly lands exactly on a half-cent tie

from decimal import Decimal, ROUND_HALF_UP

charge = Decimal("0.05")
split = charge / 2
print("exact split:", split)
print("default quantize to cents:", split.quantize(Decimal("0.01")))
print("half-up quantize to cents:", split.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP))
exact split: 0.025
default quantize to cents: 0.02
half-up quantize to cents: 0.03

Measured: splitting a 5-cent charge two ways gives an exact 0.025, a genuine halfway value at the cent boundary -- a totally ordinary split-the-bill or fee-sharing calculation, not a contrived edge case. The default mode rounds it down to 0.02; ROUND_HALF_UP rounds it up to 0.03. Two people splitting that charge under the default mode would see their two cents not add back up to the original five (0.02 + 0.02 = 0.04), a one-cent discrepancy that's exactly the kind of thing accounting reconciliation catches and support tickets get filed over. If a business or legal rule expects "round half up" (most point-of-sale and accounting conventions do), pass rounding=ROUND_HALF_UP explicitly rather than relying on the module default.

Frequently asked questions

Does Decimal.quantize() round 2.5 up to 3 by default?

No -- we measured Decimal('2.5').quantize(Decimal('1')) returning 2 under Python's default context. The default rounding mode is ROUND_HALF_EVEN (banker's rounding), which rounds exact halfway values to the nearest even neighbor, not always upward.

What is the default rounding mode for Python's decimal module?

ROUND_HALF_EVEN -- we confirmed this via decimal.getcontext().rounding, and measured it rounding 0.5 to 0 and 2.5 to 2, while 1.5 and 3.5 both round to the even value 2 and 4 respectively.

How do I get round-half-up behavior with Decimal.quantize()?

Pass rounding=ROUND_HALF_UP explicitly, e.g. d.quantize(Decimal('0.01'), rounding=ROUND_HALF_UP). We measured this correctly rounding 0.5 to 1 and 2.5 to 3, matching conventional school and point-of-sale rounding rules.

Why didn't my rounding bug show up in testing?

ROUND_HALF_EVEN and ROUND_HALF_UP only disagree on values that land exactly on a half, like 2.5 -- every other value rounds identically under both modes. We measured this directly, which is why test cases that don't happen to hit an exact tie won't reveal the difference.

Is banker's rounding (ROUND_HALF_EVEN) wrong for financial calculations?

Not inherently -- it's the IEEE 754 / general decimal arithmetic standard default, chosen to avoid statistical bias across many roundings. But most point-of-sale, invoicing, and tax conventions expect round-half-up, so relying on the decimal module's default without checking which one your business rule requires is the real risk we measured.
