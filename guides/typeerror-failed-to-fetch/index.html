TypeError: Failed to fetch (tested)

TypeError: Failed to fetch is what Chrome's fetch() throws when no usable response came back. We reproduced 15 different causes in Chromium 153. Every one of them produced exactly the same message. The real reason is only in the DevTools console and Network tab, never in the error object.

1. The short answer

The message tells you almost nothing. In our tests CORS errors, a server that was down, a DNS failure, a bad certificate, mixed content, an ad-blocker block, a CSP block, an offline browser and a dropped connection all threw the same thing:

TypeError: Failed to fetch

The error had no cause (it was undefined). Your JavaScript cannot see which case it was. That is on purpose: if a page could tell "CORS blocked" from "host does not exist", it could scan networks it should not see.

To find the cause, open DevTools. The Console shows a line like Failed to load resource: net::ERR_CONNECTION_REFUSED or a CORS message. The Network tab shows the same code in the Status column.

2. Our test setup

A page on http://app.test:8983 called fetch() on http://api.test:8983 (a different origin), or on HTTPS port 8984 with a self-signed certificate. Both names pointed to 127.0.0.1 through Chromium's --host-resolver-rules. For each case we logged the thrown error, the console lines and Playwright's requestfailed reason. The server logged which requests actually arrived.

try {
  await fetch('http://api.test:8983/nocors');
} catch (e) {
  console.log(e.name, e.message, e.cause); // TypeError Failed to fetch undefined
}

One more trap: when the body was cut short (Content-Length 100, only 3 bytes sent), fetch() itself resolved with status 200. The error came later, from await response.text(), as TypeError: Failed to fetch with net::ERR_CONTENT_LENGTH_MISMATCH in the console. If the stack trace points at .json() or .text(), suspect a dropped connection mid-body.

7. A quick debugging order

  1. Open DevTools > Console and read the line just before or after the error. It names the real cause.
  2. Open the Network tab, click the failed request, and look at the Status column (e.g. (failed) net::ERR_... or CORS error).
  3. Run the same request with curl -i. If curl gets a normal answer, it is a browser-side rule: CORS, mixed content, CSP or an extension.
  4. If curl fails too, it is the network or server: DNS, refused, cert or reset.
  5. Check the API's response headers with our HTTP header checker to see if CORS headers are there.

Frequently asked questions

Why does fetch say 'Failed to fetch' with no details?

Browsers hide the reason from JavaScript so pages cannot probe networks. In our Chromium 153 tests, 15 different causes gave the same message and e.cause was undefined. The real reason is in the DevTools console and Network tab.

Is 'Failed to fetch' always a CORS error?

No. CORS is common, but we got the identical error from a server that was down, a DNS failure, a bad certificate, mixed content, an ad blocker, CSP, being offline and a dropped connection. Read the console line to tell them apart.

Why does the request work in curl or Postman but fail in the browser?

CORS, mixed content and CSP are browser rules. In our CORS test the server received the request and answered 200, but Chromium refused to give the response to the page. curl does not apply those rules.

Does a 404 or 500 cause 'Failed to fetch'?

Not by itself. With CORS headers present, fetch resolved and response.ok was false. But a 500 without CORS headers threw 'Failed to fetch' with a CORS message, because error pages often skip the CORS headers.

What is the Node.js version of this error?

Node 24 throws 'TypeError: fetch failed'. Unlike the browser, it puts the reason in e.cause: for example code ECONNREFUSED, ENOTFOUND, ECONNRESET, UND_ERR_SOCKET or DEPTH_ZERO_SELF_SIGNED_CERT.
