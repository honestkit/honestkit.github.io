Access-Control-Allow-Headers (tested)

Access-Control-Allow-Headers goes on the response to a CORS preflight and lists the request headers the real request may carry. We tried eight header values against four cross-origin POSTs and logged what reached the server.

1. The results

Page at http://localhost:8973, cross-origin fetch() POST to http://127.0.0.1:8974. Every response carried Access-Control-Allow-Origin: * (or the exact origin plus Access-Control-Allow-Credentials: true in the credentials row). "OK" means OPTIONS then POST reached the server and fetch resolved; "blocked" means only the OPTIONS preflight arrived and fetch threw TypeError: Failed to fetch.

The preflight's Access-Control-Request-Headers arrived lowercase (content-type, x-api-key, authorization). Each blocked request produced this console error:

Access to fetch at 'http://127.0.0.1:8974/x1' from origin 'http://localhost:8973' has been blocked by CORS policy: Request header field content-type is not allowed by Access-Control-Allow-Headers in preflight response.

2. What this means

  • JSON needs it. Content-Type: application/json is not a safelisted value, so it triggers a preflight and must be listed. text/plain is safelisted and never sent a preflight.
  • Header names are case-insensitive. content-type and Content-Type behaved identically.
  • Only listed headers pass. Allowing x-api-key did not allow Content-Type or Authorization; list every non-safelisted header the request sends.
  • * is a wildcard only without credentials. With credentials: 'include', * was treated literally and every preflighted request was blocked. In this Chromium build, plain * without credentials also let Authorization through; the Fetch spec says the wildcard does not cover Authorization, so *, Authorization is the portable form.

3. Answering OPTIONS in nginx (not executed)

This snippet is doc-based; we did not run it.

location /api/ {
    if ($request_method = OPTIONS) {
        add_header Access-Control-Allow-Origin "https://app.example.com" always;
        add_header Access-Control-Allow-Methods "GET, POST, PUT, PATCH, DELETE" always;
        add_header Access-Control-Allow-Headers "Content-Type, Authorization, X-Api-Key" always;
        add_header Access-Control-Max-Age 600 always;
        add_header Vary Origin always;
        return 204;
    }
    add_header Access-Control-Allow-Origin "https://app.example.com" always;
    add_header Vary Origin always;
    proxy_pass http://backend;
}

Frequently asked questions

Why does my JSON POST fail CORS?

Content-Type: application/json triggers a preflight. In our Chromium 153 test it was blocked with 'Request header field content-type is not allowed by Access-Control-Allow-Headers in preflight response' until the preflight answered Access-Control-Allow-Headers: Content-Type.

Is Access-Control-Allow-Headers case-sensitive?

No. content-type and Content-Type both allowed a JSON POST in our test.

Does Access-Control-Allow-Headers: * work with credentials?

No. With credentials: 'include' plus an exact origin and Allow-Credentials: true, * was treated literally and JSON, X-Api-Key and Authorization requests were all blocked. List the headers explicitly.

Does * cover the Authorization header?

In Chromium 153 without credentials it did. The Fetch spec excludes Authorization from the wildcard, so send '*, Authorization' (which also worked) or list it explicitly.
