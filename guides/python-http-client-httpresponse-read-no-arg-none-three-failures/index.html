http.client resp.read() on a Transient None: 3 Different Failures (tested)

A non-blocking raw stream signals "no data ready yet" by returning None -- distinct from the empty read that means real end-of-stream. We fed http.client.HTTPResponse.read() (no argument -- the call behind most urlopen(url).read() code) one such None before a valid body. With Content-Length it crashed with TypeError: object of type 'NoneType' has no len(); with chunked encoding it raised IncompleteRead(0 bytes read); with no length it returned None and closed the connection. Three framings, three unrelated-looking errors, one cause.

1. One transient None, three framings, three different results

import http.client, io

class FlakyRaw(io.RawIOBase):
    """Sends headers cleanly, then one transient None, then the body."""
    def __init__(self, header_bytes, body_bytes):
        self.header_bytes, self.body_bytes, self.stage = header_bytes, body_bytes, 0
    def readable(self):
        return True
    def readinto(self, b):
        if self.stage == 0:
            n = len(self.header_bytes)
            b[:n] = self.header_bytes
            self.stage = 1
            return n
        if self.stage == 1:
            self.stage = 2
            return None            # transient: no data ready yet
        if self.stage == 2:
            n = len(self.body_bytes)
            b[:n] = self.body_bytes
            self.stage = 3
            return n               # the real, complete body
        return 0                   # real EOF after that

class FakeSocket:
    def __init__(self, raw):
        self.raw = raw
    def makefile(self, mode, *a, **kw):
        return io.BufferedReader(self.raw)
    def close(self):
        pass
    def sendall(self, data):
        pass

body = b"hello body"
cases = [
    ("Content-Length", b"HTTP/1.1 200 OK\r\nContent-Length: 10\r\n\r\n", body),
    ("chunked", b"HTTP/1.1 200 OK\r\nTransfer-Encoding: chunked\r\n\r\n", b"a\r\nhello body\r\n0\r\n\r\n"),
    ("no length", b"HTTP/1.1 200 OK\r\nConnection: close\r\n\r\n", body),
]
for framing, headers, wire_body in cases:
    conn = http.client.HTTPConnection("example.com")
    conn.sock = FakeSocket(FlakyRaw(headers, wire_body))
    conn.request("GET", "/")
    resp = conn.getresponse()
    try:
        data = resp.read()
        print(f"{framing:15} returned {data!r}, connection closed: {resp.fp is None}")
    except Exception as e:
        print(f"{framing:15} {type(e).__name__}: {e}")
Content-Length  TypeError: object of type 'NoneType' has no len()
chunked         IncompleteRead: IncompleteRead(0 bytes read)
no length       returned None, connection closed: True

Measured: every body is valid and complete, one read away. The same resp.read() call crashed with a generic TypeError, raised IncompleteRead as if the server had cut the body short, or returned None -- which read() is documented never to return -- and closed the connection. Which one you get depends only on how the server framed the body.

2. Why each framing fails differently

FramingCode path in http/client.pyWhat the None does
Content-Length_safe_read(self.length): data = self.fp.read(cursize) then if len(data) >= amtlen(None) raises TypeError before the short-read check that would raise IncompleteRead
Transfer-Encoding: chunked_read_next_chunk_size(): line = self.fp.readline(...) then int(line, 16)BufferedReader.readline() collapses the None to b''; int(b'', 16) fails and is re-raised as IncompleteRead(0 bytes read)
no length (read until close)s = self.fp.read() then self._close_conn()BufferedReader.read() returns the None as-is; read() closes the connection and hands you None

Only the chunked case produces an http.client exception, and it blames the server ("incomplete read"). The Content-Length case points at a len() call inside the standard library. The no-length case raises nothing, so the failure surfaces later, wherever your code first treats the None as bytes. In all three the connection is unusable afterwards, so the body cannot be re-read.

3. The fix: stop the None below http.client

Append to the script above:

class RetryOnNone(io.RawIOBase):
    """Wraps a non-blocking raw stream; turns None into 'wait and retry'."""
    def __init__(self, raw):
        self.raw = raw
    def readable(self):
        return True
    def readinto(self, b):
        while True:
            n = self.raw.readinto(b)
            if n is not None:
                return n
            # real code: wait for readability here (e.g. selectors) instead of spinning

class FixedSocket(FakeSocket):
    def makefile(self, mode, *a, **kw):
        return io.BufferedReader(RetryOnNone(self.raw))

for framing, headers, wire_body in cases:
    conn = http.client.HTTPConnection("example.com")
    conn.sock = FixedSocket(FlakyRaw(headers, wire_body))
    conn.request("GET", "/")
    print(f"{framing:15}", conn.getresponse().read())
Content-Length  b'hello body'
chunked         b'hello body'
no length       b'hello body'

Measured: same flaky streams, and all three framings return the full body. The retry has to live in the raw stream that makefile() hands to http.client; once a None reaches HTTPResponse the connection is already lost. Simpler: if you control the socket, keep it blocking (or use settimeout()), which never returns None.

Frequently asked questions

Does urllib.request.urlopen() hit this too?

urlopen() returns an http.client.HTTPResponse for http and https URLs, so .read() on it runs the same code. With urlopen's default blocking sockets you won't see a None; it happens when the socket or the stream from makefile() is non-blocking, e.g. a custom connection class or an event-loop integration.

Is the server sending a truncated body?

No. In all three repros the body is complete and correctly framed. IncompleteRead(0 bytes read) and the closed connection come from the client treating a transient None as end-of-data.

Why TypeError instead of IncompleteRead for Content-Length?

_safe_read() calls len(data) on the result of self.fp.read() before its short-read check. When that result is None, len() raises TypeError first, so the IncompleteRead branch, and HTTPResponse.read()'s except IncompleteRead cleanup, never run.

Can I catch the error and call read() again?

No. Once HTTPResponse has seen the None, the connection is closed or the response is in an inconsistent state, and the remaining body is not recoverable from that response object. Retry the whole request, or fix the stream below http.client as shown.

Is this related to the other None/EOF findings?

Yes -- same family as json.load(), configparser.read_file(), http.server and others: a correctly-returned non-blocking None is treated as end-of-data one layer above io. This one is notable because a single call fails three different ways depending on response framing.
